Pillar Overview

📌 Purpose

This pillar builds genuine Linux command-line proficiency from first principles. Linux is the operating system that powers the vast majority of servers, cloud infrastructure, and DevOps tooling. Mastering the CLI is not optional — it is the primary interface you will use to navigate, configure, and troubleshoot systems throughout your career.

Every concept here is learned through hands-on practice. The knowledge transfers directly to AWS (EC2 instances, container hosts, automation scripts) and to the full DevOps roadmap (Dockerfile commands, Kubernetes pod debugging, CI/CD pipeline scripting).

🎯 Learning objectives
  • Navigate the Linux filesystem using absolute and relative paths
  • Create, copy, move, and delete files and directories safely
  • Understand and modify file permissions (chmod, chown, umask)
  • Manage processes (ps, top, kill, jobs, bg, fg)
  • Connect to remote systems using SSH and manage keys
  • Install, update, and remove software using package managers (apt, yum, dnf)
  • Write bash scripts with variables, conditionals, loops, and functions
  • Manage system services with systemd (systemctl, journalctl)
  • Use text processing tools (grep, sed, awk) for log analysis and data extraction
  • Troubleshoot network issues with commands like ping, traceroute, netstat, ss, and curl

Filesystem Structure & Navigation

A filesystem is how the operating system organises data on disk into a structured hierarchy. On Linux, this is a single tree with one root — everything lives under it. Unlike Windows, which gives each disk its own tree (C:\, D:\), Linux has one unified tree for all disks, partitions, and even devices.

The top of the tree is written as / (called "root"). All files, directories, and devices live somewhere below it.

💡 Key insight Even a USB drive or a CD‑ROM is mounted somewhere inside this tree, not given a separate drive letter.

The Filesystem Hierarchy Standard (FHS) defines the structure of Linux directories. Every Linux distribution follows it, so you'll find the same layout on Ubuntu, Debian, RHEL, Fedora, and even container images.

/procVirtual filesystem for process and kernel info/proc/cpuinfo, /proc/meminfo

💡 Tab completion Press Tab to auto‑complete file/directory names. Press twice to see possible matches.

Absolute path: Full address starting from root, always starts with /. Works the same no matter where you are.

Relative path: Address starting from your current working directory. Uses . and ...

# Assuming you are in /home/user/projects

# Absolute path (starts with /)
cd /var/log

# Relative path (no leading /)
cd ../../etc          # go up two levels, then into etc
cd ./scripts          # same as just "cd scripts" (./ is optional)
⚠️ Common mistake Forgetting the leading / makes the path relative. cd etc will look for an etc directory inside your current directory, not the system /etc.
Path decision tree
  • Does the path start with /? → Absolute (works anywhere)
  • No leading / → Relative (depends on current directory)

Any file or directory whose name starts with . is hidden. Hidden = not shown by default in ls. Not protected or encrypted — just kept out of the way.

ls -a ~     # reveal hidden files in home
ls -la ~    # hidden files + long format
File/DirPurpose
.bashrcBash shell config — runs every time a terminal opens
.profileLogin shell config
.gitconfigGit settings — name, email, preferences
.ssh/SSH keys and known hosts
.The current directory itself
..The parent directory

Displays an entire directory structure visually — not just one level at a time.

tree ~              # full tree of home directory
tree -L 1 /         # 1 level deep from root
tree -L 2 /home     # 2 levels deep from /home
tree -a ~           # include hidden files
tree -d ~           # directories only, no files
💡 -L (Level) is the most useful flag — always use it on large directories to avoid thousands of lines of output.

If tree is not installed: sudo apt install tree (Debian/Ubuntu) or sudo dnf install tree (RHEL/Fedora).

File & Directory Operations

touch notes.txt                    # creates empty file (or updates timestamp)
touch file1.txt file2.txt          # create multiple at once
echo "hello world" > notes.txt    # writes content, overwrites entire file
echo "another line" >> notes.txt  # appends to file, preserves existing content
OperatorBehaviour
>Wipes the file, writes fresh
>>Keeps existing content, adds to the bottom
⚠️ Warning: > is destructive — it wipes the entire file, not just one line. Always double‑check before using.
mkdir projects
mkdir docs notes images            # multiple at once
mkdir -p projects/linux/section-2  # creates full nested path in one shot
💡 -p (parents) creates all missing parent directories along the way. Without it, mkdir a/b/c fails if a/b doesn't already exist.
cp source destination
cp notes.txt backup/                     # copy into directory
cp notes.txt backup/notes-copy.txt       # copy and rename at the same time
cp -r projects projects-backup           # -r required for directories
cp -i notes.txt backup/                  # interactive — asks before overwriting
FlagMeaning
-rRecursive — required for directories
-iInteractive — prompts before overwriting
💡 -i is a safety net. Use it when unsure whether the destination already has a file with the same name.
mv source destination
mv notes.txt archive/               # move into directory (same as cut+paste)
mv old-name.txt new-name.txt        # rename in same location
mv notes.txt archive/renamed.txt    # move and rename in one step
mv projects archive/                # move a directory (no -r needed)
mv -i notes.txt archive/            # interactive — asks before overwriting
Note: Unlike cp, mv leaves no copy behind — the original is gone. Unlike cp, mv doesn't need -r for directories.
rm notes.txt                         # delete a file
rm file1.txt file2.txt               # delete multiple files
rm -i notes.txt                      # interactive — asks for confirmation
rm -r projects/                      # delete a directory and all its contents
rm -rf projects/                     # force delete — no prompts, no mercy (dangerous!)
rmdir empty-dir/                     # only works if the directory is empty
CommandBehaviour
rmDeletes files
rm -rDeletes a directory and everything inside it
rm -rfForce deletes — no confirmation, no recovery
rmdirDeletes a directory only if it is empty — safe option
⚠️ Linux has no recycle bin. Deleted = gone permanently. rm -rf is the most dangerous command — always double‑check the path before running.
💡 Safety tip: Some users alias rm to rm -i to prevent accidental deletion. Use rmdir for directories you want to delete safely.
WildcardMatchesExample
*Any number of characters (including zero)*.txt → all text files
?Exactly one characterfile-?.txt → file-1.txt, file-a.txt (not file-10.txt)
 
rm *.log                               # delete all .log files
cp *.txt backup/                       # copy all .txt files into backup/
ls file-?.txt                          # matches file-1.txt, file-a.txt
ls chapter-*.md                        # list all markdown files starting with "chapter-"
⚠️ Caution with rm *: Always run ls * first to see what you're about to delete.
cat notes.txt                          # print entire file to screen (good for short files)
less notes.txt                         # scrollable viewer (Space=down, b=up, q=quit, /search)
head -n 5 notes.txt                    # first 5 lines
tail -n 5 notes.txt                    # last 5 lines
tail -f app.log                        # follow — prints new lines as file grows (great for logs)
KeyAction in less
Space or fPage down
bPage up
qQuit
/wordSearch for "word"
nNext search result
NPrevious search result
💡 Use less for large files — cat will flood your terminal with thousands of lines. less loads the file page by page.
tail -f is essential for watching log files in real time.

Linux doesn't rely on file extensions to know what a file is. Use file to identify what something actually contains.

file unknown.bin                       # tells you if it's ASCII text, binary, image, etc.
file script.sh                         # might show "Bourne-Again shell script"

Permissions & Ownership

MetadataDescription
User owner (u)The creator or assigned owner of the file — usually the user who created it.
Group owner (g)A collection of users who share access. The file's group determines which users get group‑level permissions.
Three sets of permissionsSeparate rwx triples for the user owner, the group owner, and everyone else (other)
 
$ ls -l /etc/shadow
-rw-r----- 1 root shadow 1234 Mar 10 10:00 /etc/shadow

# Only root (owner) and the shadow group can read. No one else.
$ ls -ld /root
drwx------ 5 root root 4096 Mar 10 10:00 /root/

# Only root can enter /root — completely locked.
💡 Key insight Permissions are not just for security — they also protect against accidental changes. A missing execute bit on a directory prevents cd into it, which stops you from even seeing what's inside.
PermissionSymbolOn a fileOn a directory
ReadrView contentsList contents with ls
WritewModify or deleteCreate, delete, rename files inside
ExecutexRun as a programEnter with cd
💡 Directory execute You need x on a directory just to cd into it — even if you have r.
# Example: a directory with r but no x
$ chmod 444 mydir/          # r--r--r--
$ cd mydir/
bash: cd: mydir/: Permission denied   # cannot enter

$ chmod 555 mydir/          # r-xr-xr-x (adds execute)
$ cd mydir/                 # now works
d  rwx  r-x  r-x
│   │    │    │
│   │    │    └── other
│   │    └─────── group
│   └──────────── user (owner)
└──────────────── type: d=directory  -=file  l=symlink

Each block of three is always r then w then x. A - means that permission is not granted.

OutputMeaning
-rw-r--r--File. Owner: read+write. Group: read. Other: read.
drwxr-xr-xDirectory. Owner: full. Group: read+execute. Other: read+execute.
drwx------Directory. Owner: full. Group: none. Other: none.
drwxrwxrwtDirectory. Everyone: full. Sticky bit set (t).
Real system examples
  • /etc/hosts → -rw-r--r-- (root edits, everyone reads)
  • /etc/passwd → -rw-r--r-- (user list public)
  • /tmp → drwxrwxrwt (shared, sticky bit prevents deleting others' files)
  • /root → drwx------ (admin's home, locked to everyone else)

Syntax: chmod [who][operator][permission] filename

WhoOperatorPermission
u user+ addr read
g group- removew write
o other= set exactlyx execute
a all
 
chmod u+x script.sh          # add execute for owner
chmod g-w notes.txt          # remove write from group
chmod o=r notes.txt          # set other to read only
chmod a+r notes.txt          # give everyone read
chmod u+x,g-w notes.txt      # multiple changes at once
💡 Tip chmod a+x file adds execute for everyone (user+group+other).
PermissionValue
r4
w2
x1
none0

Add values for each category (user, group, other) to form a three-digit number.

NumberPermissionsCalculation
7rwx4+2+1
6rw-4+2+0
5r-x4+0+1
4r--4+0+0
0---0+0+0
 
chmod 755 script.sh     # rwxr-xr-x — scripts, directories
chmod 644 notes.txt     # rw-r--r-- — regular files, config files
chmod 700 private.txt   # rwx------ — owner only, full access
chmod 600 secret.txt    # rw------- — owner read+write only
chmod 777 shared.txt    # rwxrwxrwx — full access for everyone (dangerous)
Memorise these two: 755 for scripts/directories, 644 for regular files.
chown newowner filename
chown user:group filename          # change both at once
chown -R user:group directory/     # recursive — apply to whole directory

Examples:

sudo chown root notes.txt          # make root the owner
sudo chown codespace notes.txt     # give back to codespace
sudo chown codespace:root notes.txt # owner=codespace, group=root
⚠️ Requires sudo Only root can transfer ownership of files. A regular user cannot take ownership away from root without sudo.
chgrp newgroup filename
chgrp root notes.txt               # assign to root group
chgrp -R codespace projects/       # recursive
Note: chown user:group does both at once, so chgrp is rarely needed.

sudo (superuser do) lets an authorised user run a single command with root privileges.

sudo chown root notes.txt          # run as root
sudo chmod 600 /etc/hosts          # modify a system file
TermMeaning
rootThe administrator account — no permission restrictions
sudoAllows a regular user to act as root for one command
sudoersThe list of users allowed to use sudo
💡 Tip: sudo asks for your password the first time, then remembers for a few minutes.

Set other to read onlychmod o=r file
Common file permissionschmod 644 file
Common script permissionschmod 755 file

Users & Groups

Every process that runs on Linux runs as a specific user. Every file is owned by a specific user. Users are how Linux tracks who is doing what and enforces permissions.

TypeDescriptionExample
RootThe superuser — no restrictionsroot
RegularHuman users with home directoriescodespace
SystemCreated by software, not humans — run background serviceswww-data, nobody
📌 Key insight The root user has full system access. System users run background services and typically have no login shell (/sbin/nologin).

A group is a collection of users. Instead of setting permissions for each user individually, you put users in a group and set permissions on the group once.

Every user has:

  • One primary group — assigned at creation, same name as the user by default
  • Zero or more supplementary groups — additional groups they belong to
💡 Real example The codespace user belongs to its own primary group, plus supplementary groups created by installed tools — docker, python, golang, nvm, ssh, and more. Each tool creates a group and adds the user to it so commands work without needing sudo every time.

/etc/passwd — the user database

Passwords are not stored here despite the name. Each line is one user:

codespace:x:1000:1000::/home/codespace:/bin/bash
      │         │ │    │    │ │              └── login shell
      │         │ │    │    │ └── home directory
      │         │ │    │    └── comment (usually full name)
      │         │ │    └── primary group ID (GID)
      │         │ └── user ID (UID)
      │         └── password placeholder (x = stored in /etc/shadow)
      └── username

/etc/group — the group database

codespace:x:1000:
      │         │ │    └── members (comma-separated)
      │         │ └── group ID (GID)
      │         └── password placeholder
      └── group name

/etc/shadow — actual passwords

Stores hashed passwords. Only readable by root — this is where real password security lives.

⚠️ Security note /etc/shadow is readable only by root (-rw-r-----). This is why passwords are stored there and not in /etc/passwd.
CommandWhat it doesExample output
whoamiPrints your username only — deliberately simple, no flagscodespace
idPrints UID, GID, and every group you belong to in one shotuid=1000(codespace) gid=1000(codespace) groups=1000(codespace),989(docker),988(golang)
groupsPrints just the group names — a simpler view than idcodespace pipx python oryx golang docker
💡 Consistency check All three commands should agree with what's in /etc/passwd and /etc/group — they're just different views of the same underlying data.

All of these require sudo since they affect the whole system.

useradd — create a new user

sudo useradd newuser                    # minimal — NO home directory created
      sudo useradd -m newuser                 # create WITH a home directory
      sudo useradd -m -s /bin/bash newuser    # also set login shell
      sudo useradd -m -s /bin/bash -G docker devuser   # add to a group at creation
FlagMeaning
-mCreate a home directory
-sSet the login shell
-gSet primary group
-GSet supplementary groups (comma-separated)
⚠️ Without -m, no home directory is created. Almost always use -m.

usermod — modify an existing user

sudo usermod -aG docker existinguser    # ADD to the docker group
      sudo usermod -s /bin/bash existinguser  # change their shell
      sudo usermod -l newname oldname         # rename the user
⚠️ -aG vs -G -aG appends to a group. Without -a, -G replaces all their supplementary groups instead of adding one — a common mistake. The group must already exist via groupadd before you can add anyone to it.

userdel — delete a user

sudo userdel newuser           # delete user, leave home directory behind
      sudo userdel -r newuser        # delete user AND their home directory
sudo groupadd developers          # create a new group
      sudo groupmod -n newname oldname  # rename a group
      sudo groupdel developers          # delete a group
⚠️ Can't delete a group that is still set as someone's primary group — change their primary group first.

Adding / removing a user from a group — two ways

sudo usermod -aG developers testuser    # add via usermod
      sudo gpasswd -a testuser developers     # add via gpasswd
      sudo gpasswd -d testuser developers     # remove via gpasswd
💡 Verify with the source, not a summary. groups username is a useful quick check, but when in doubt, check /etc/group directly: 
cat /etc/group | grep -E "developers|devteam"

This caught a real typo during practice — a command created a stray group called sevelopers instead of developers. Linux doesn't validate group names against what you "meant" — a typo in a group-creating command silently creates a brand new real group. Always double check with /etc/group if something looks off.

sudo passwd testuser        # set or change testuser's password (as admin)
      passwd                      # change YOUR OWN password (no sudo needed)
      sudo passwd -l testuser     # lock the account (disable login)
      sudo passwd -u testuser     # unlock it
      sudo passwd -d testuser     # delete the password entirely (risky — no password required to log in)
📌 Note Typed characters don't show on screen when entering a password — that's normal, not a glitch.

su stands for switch user.

su testuser           # switch to testuser, asks for THEIR password
      su - testuser          # switch AND load their environment (home dir, shell config)
      exit                   # return to your previous user
⚠️ The - matters. Without it, you keep your old environment but act as the new user. Always use su - username.

sudo -i and sudo -u

sudo -i                   # become root entirely, with root's own environment
      sudo -u testuser whoami   # run ONE command as testuser, then return immediately
💡 sudo -u is the one used most in real work — running a single command as someone else without fully switching sessions.
📌 Container environments In a containerized environment like Codespaces, su - user may not behave exactly like a standard Linux server (e.g. pwd may not land in their home directory as expected). The command itself is correct — the container environment is the variable.

  1. /etc/passwd stores user info, not passwords. /etc/shadow stores the real (hashed) passwords.
  2. Every user has exactly one primary group and any number of supplementary groups.
  3. A group must exist (groupadd) before you can add anyone to it.
  4. usermod -aG appends to groups. Leaving off -a replaces them entirely — a destructive mistake.
  5. Typos in group names don't error — they silently create new, real groups. Verify against /etc/group when unsure.
  6. su - username (with the dash) loads the target user's full environment. Without it, you keep your own.
  7. sudo -u username command runs a single command as someone else — the most common real-world use case.
